# Spec: Evidence-Augmented Hybrid Retrieval (EAHR) — v2

## 1. Problem Statement

Event memory systems (ETEC+QEMR) underperform raw vector RAG on detail-retrieval QA:

| Method | EM (LongMemEval 50q) |
|---|---|
| vector_rag | 0.56 |
| full (ETEC+QEMR) | 0.48 |

**Root cause** (verified by 3 independent agents, no code bugs):
- Event extraction produces paraphrased summaries that lose specific details
- Reader prompt already includes evidence quotes (Phase 1 already implemented) but the quotes don't always contain the answer
- 7/8 failures due to extraction abstraction; 1/8 due to session skipping

**Key insight**: The evidence quotes in the reader are not sufficient because:
1. The extraction LLM doesn't always extract events from all sessions
2. When events exist, the `content` field is too abstract
3. The raw turn text that contains the answer is never stored or retrieved

## 2. What's Already Done (Phase 1)

The `_reader_messages()` function already includes evidence quotes:

```python
quotes = [ref.quote for ref in refs if ref.quote]
if quotes:
    parts.append("source: " + " | ".join(quotes))
```

**This did not close the gap** because the extraction LLM doesn't always extract events from the sessions containing the answer. The evidence quotes are only available for events that were extracted.

## 3. Proposed Approach: Dual-Path Retrieval

### 3.1 Core Idea

Instead of relying solely on event memories, retrieve **both** event memories AND raw turn chunks. Merge and deduplicate.

```text
Query
  │
  ├── Path A: Event Retrieval (QEMR) ──> Events + evidence quotes
  │
  ├── Path B: Raw Turn Retrieval (vector_rag style) ──> Top-K raw chunks
  │
  └── Merge & Deduplicate ──> Combined context ──> Reader
```

### 3.2 Why This Works

- **Path A** provides structured, temporal, entity-rich information
- **Path B** provides raw text with specific details (names, numbers, dates)
- The reader gets both, enabling it to answer detail-retrieval questions

### 3.3 Implementation

**Approach: Benchmark-level composition** (least invasive, fastest to validate)

In `benchmarks/longmemeval/run.py`, add a `full_dual` method:
1. Run QEMR on event store (existing code)
2. Run vector_rag on raw turn store (existing code)
3. Merge `reader_messages` from both results
4. Deduplicate by content hash
5. Truncate to shared token budget

No core service changes needed for validation.

### 3.4 Success Criteria

| Criterion | Target | Measurement |
|---|---|---|
| full_dual EM >= vector_rag EM | >= 0.56 | LongMemEval 50q |
| No LoCoMo degradation | >= 0.0634 | LoCoMo 1986q |
| Token cost | <= 1.5x vector_rag | Per-query tokens |
| Evidence provenance preserved | 100% | Packed items with raw_turn_id |

## 5. Research Positioning

### 5.1 What's Novel

EAHR is not a new retrieval paradigm. It is:
- A **practical response** to a documented negative result
- The first to show that evidence-constrained event memory needs dual-path retrieval to match raw RAG
- A quantification of the extraction-abstraction gap

### 5.2 Paper Structure

**Title**: "Why Event Memory Underperforms Raw RAG on Detail Retrieval"

1. **Negative result**: Event memory EM=0.48 vs vector_rag=0.56
2. **Root cause**: Extraction abstraction (verified by 3 independent agents)
3. **Remediation**: Dual-path retrieval (EAHR)
4. **Results**: full_dual EM >= vector_rag, with preserved temporal capabilities
5. **Lessons**: Extraction quality is the bottleneck, not retrieval or consolidation

### 5.3 Experiments a Reviewer Would Expect

**Mandatory**:
- LoCoMo full evaluation (1986q)
- Per-type stratified analysis (knowledge-update, temporal-reasoning, multi-session, single-session)
- Ablation table: vector_rag / event-only / event+ETEC / event+ETEC+dual
- Bootstrap CIs on all numbers

**Strongly expected**:
- Reader model variation (mimo-v2.5 + one stronger model)
- Budget sensitivity (1024, 2048, 4096, 8192)
- Evidence quote length sensitivity (100, 200, 300, 500 chars)
- At least one external baseline comparison (cite Mem0 published numbers)

## 6. Risk Analysis

| Risk | Mitigation |
|---|---|
| Dual retrieval increases latency | Parallel execution; cache embeddings |
| Raw chunks redundant with events | Deduplicate by content hash |
| Token budget exceeded | Budget-aware merging with priority |
| Extraction still loses details | Raw chunks provide fallback |
| No improvement over vector_rag | Fallback to vector_rag-only for detail queries |
