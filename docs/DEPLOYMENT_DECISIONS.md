# 部署形态与多租户决策分析

> 本文档分析 EvoEventMem 的部署形态选择：多租户是否必要、在线部署的商业意义、以及这些决策对简历叙事的影响。基于工程事实与竞品情报，不虚构市场数据。

## 1. 多租户：为什么做，为什么不做

### 1.1 我们已有的多租户能力（已实现，非计划）

代码中已实现并测试通过：
- `RequestScope`（tenant_id + user_id 必填，session_id 可选）——API 层强制
- 所有 UUID 查询必须携带 scope；跨租户返回 404（不泄露存在性）
- PostgreSQL 层：`tenant_id/user_id/session_id` 参与每条 SQL 过滤
- 测试覆盖：`tests/api/test_request_scope.py`、`tests/infra/test_async_repository_contract.py` 跨租户隔离用例

### 1.2 多租户的价值（诚实分析）

**有必要的场景**：
1. **多 Agent 共享部署**：一个团队内多个 Agent（研究、编码、运维）共用一套记忆服务，各自隔离
2. **个人多项目**：一个用户多个项目/会话域，记忆不串
3. **演示/面试**：能证明"我知道隔离为什么重要"——**这是工程判断力的展示点**，不是产品卖点

**不充分的场景（用户的直觉正确）**：
- 单用户本地使用：多租户是纯开销
- 没有真实用户时：多租户是"为不存在的问题做的设计"

**结论**：多租户**已实现**是低成本事实（一个 scope 参数贯穿存储/服务/API），它证明的是**安全设计意识**，不主张"我们做了一个多租户 SaaS"。

### 1.3 在线部署的商业意义（核实结果）

竞品现状：
- Mem0：library（免费）/ self-hosted（免费）/ **cloud platform（付费，含专有优化）**——基准高分只对 managed platform 保证
- Zep：enterprise 付费
- TencentDB Agent Memory：**MIT 开源 + 腾讯云生态**（开源获客，云服务变现的典型打法）
- Letta：cloud（Constellation）付费 + self-host

**趋势确认**：记忆层正在"可插件 → 基础组件"化，头部玩家都有托管形态。**但**：它们卖的是"托管的便利 + 团队协作"，不是"记忆算法本身"。

**我们的现实**：
- 我们没有能力/意图做付费 SaaS（无团队、无运维资源）
- 在线部署的价值对我们是**技术验证**：证明系统能在真实服务器环境跑通（部署、迁移、持久化、故障处理）——这些我们已经在 gpu-5090 上实际做了（迁移 + 跑批）
- **"能独立部署 + 可在线运行"是简历的工程证据，不是商业模式**

## 2. 推荐部署形态（分层表述）

| 形态 | 说明 | 简历价值 |
|---|---|---|
| **本地单机**（docker compose：postgres + api + 可选本地 embedding） | 开发/个人使用 | 快速上手，证明可运行 |
| **独立服务器**（我们已做：gpu-5090 迁移） | 生产级跑批、长期运行 | 证明部署/迁移/运维能力 |
| **多租户在线**（已实现能力，按需开启） | 多 Agent/团队共享 | 证明安全设计意识 |

**不建议**：宣称"我们要做 SaaS 卖钱"——这经不起面试拷问（无用户、无收入、无差异化商业主张）。

## 3. 面试叙事：部署部分的正确讲法

**面试官会问**："你做了多租户，有真实用户吗？"

**正确回答骨架**：
1. 多租户不是产品功能，是**安全架构要求**——记忆数据是敏感的（用户偏好、项目决策），隔离是默认设计而非可选项
2. 我们用测试证明了隔离正确性（跨租户 404 不泄露存在性、scope 贯穿 SQL）
3. 独立部署 + 在线迁移实际做过（本地 → gpu-5090，容器化 + 数据迁移 + 长期跑批稳定运行）
4. 诚实承认：这不是 SaaS 尝试，是**工程完备性**的证据

## 4. 成本核算（对"要不要在线部署"的直接回答）

| 项目 | 成本 | 说明 |
|---|---|---|
| 服务器 | 已有（gpu-5090 32G 显存/62G 内存） | 跑批主力，非额外采购 |
| PostgreSQL | 容器，零成本 | docker compose |
| 嵌入模型 | 本地 qwen3-embedding-0.6b（GPU 推理） | 无需 API key；无 GPU 时可用 API 嵌入 |
| 提取/reader LLM | deepseek API（按量） | 只有评测/提取时才调用，日常查询不产生 LLM 成本 |
| 日常查询 | **零 LLM 成本**（pgvector 纯数据库检索） | 只有写入时的提取和评测需要 LLM |

**结论**：在线部署的**边际成本接近零**（复用已有服务器 + 容器化），但**日常查询零 LLM 成本**这一点是真实卖点——可以写成"检索路径零模型调用，ms 级响应，成本只发生在写入侧"。

## 5. 决策总结

- **多租户**：保留（已实现 + 测试完备），定位为"安全架构"而非"SaaS 功能"
- **在线部署**：已实际完成（gpu-5090），定位为"工程完备性证据"
- **商业模式**：不主张卖钱，主张"可独立部署的研究级系统 + 可插拔模型后端"
- **简历表述建议**：突出"部署形态完整（本地/服务器/多租户能力）+ 检索零 LLM 成本 + 证据可审计"，回避"我们做了一个竞品 SaaS"
