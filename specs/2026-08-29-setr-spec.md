# Spec: Structured Event-Text Retrieval (SETR)

> **Status**: Draft
> **Author**: opencode
> **Date**: 2026-08-29
> **Target**: Exceed vector_rag EM on LongMemEval and LoCoMo

## 1. Core Idea

**Two-stage retrieval**: First retrieve raw text (high recall), then extract structured event frames from retrieved context (high precision). The reader gets BOTH raw text AND structured events.

```text
Stage 1: Raw Retrieval
  Query → Top-K raw turn chunks (vector_rag style)
  → High recall, but no temporal structure

Stage 2: Contextual Extraction
  Retrieved chunks → LLM extracts event frames
  → Structured events with temporal info, entities, evidence spans

Stage 3: Reader
  Input: Raw chunks + Event frames + Evidence quotes
  → Answer with both detail and structure
```

## 2. Why This Beats vector_rag

vector_rag gives the reader ONLY raw chunks. SETR gives the reader:

| Component | vector_rag | SETR |
|---|---|---|
| Raw text | ✅ | ✅ (same) |
| Structured events | ❌ | ✅ (from Stage 2) |
| Temporal info | ❌ | ✅ (event timestamps) |
| Entity extraction | ❌ | ✅ (from Stage 2) |
| Evidence spans | ❌ | ✅ (character offsets) |

**On detail queries**: SETR = vector_rag (both have raw text)
**On temporal queries**: SETR > vector_rag (events have temporal structure)
**On cross-session queries**: SETR > vector_rag (events aggregate across chunks)

## 3. Key Innovation: Extract After Retrieval

**Previous approaches** (ETEC+QEMR, HyMem, xMemory):
- Extract events FROM the entire conversation
- Store events alongside raw text
- Retrieve from both stores

**SETR**:
- Retrieve raw chunks FIRST (high recall)
- Extract events FROM the retrieved chunks ONLY (focused extraction)
- Reader sees both

**Why this is better**:
1. No information loss: raw text is always available
2. Focused extraction: LLM only processes relevant chunks (faster, more accurate)
3. Events are contextualized: they inherit the temporal context of their source chunks
4. No pre-computation: events are generated per-query, not pre-stored

## 4. Implementation

### Phase 1: Contextual Extraction (2 days)

Add a post-retrieval extraction step:

```python
def extract_events_from_chunks(chunks: list[RawTurnChunk]) -> list[EventFrame]:
    """Extract structured events from retrieved raw chunks."""
    # Combine chunks into a focused context
    context = "\n".join([f"[{c.turn_id}] {c.content}" for c in chunks])
    # LLM extracts events from this focused context
    return llm_extract(context)
```

### Phase 2: Combined Reader Context (1 day)

Modify the reader prompt to include both raw chunks and event frames:

```text
[Raw Context]
[1] I've been listening to Summer Vibes on Spotify...
[2] The playlist has 45 chill tracks...

[Structured Events]
- User listens to music on Spotify (playlist: Summer Vibes, 45 tracks)
- Time: current session

[Question] What is the name of the playlist?
```

### Phase 3: Validation (2 days)

5→10→50 sample progression.

### Total: 5 days

## 5. Success Criteria

| Criterion | Target |
|---|---|
| SETR EM > vector_rag EM | > 0.56 |
| Temporal EM > vector_rag temporal EM | Positive delta |
| Token cost | <= 2x vector_rag (extra extraction cost) |
| Latency | < 30s per query (extraction is fast on focused context) |

## 6. Why This Is Novel

1. **Extract-after-retrieval** is not done by any prior work (HyMem, xMemory, HiMem all extract before retrieval)
2. **Focused extraction** on retrieved chunks is more accurate than full-conversation extraction
3. **No pre-computation** needed: events are generated per-query, so the system is always up-to-date
4. **Combines benefits**: raw text precision + event structure + temporal tracking

## 7. Comparison with Prior Work

| System | Extraction Timing | Raw Text Access | SETR Difference |
|---|---|---|---|
| vector_rag | Never | Always | SETR adds event structure |
| ETEC+QEMR | Pre-retrieval | Via evidence_refs | SETR extracts after retrieval |
| HyMem | Pre-retrieval | Dual storage | SETR extracts from retrieved context |
| xMemory | Pre-retrieval | Hierarchical | SETR is query-adaptive |
| Mnemis | Pre-retrieval | Graph-based | SETR is flat + focused |

## 9. Risks

| Risk | Mitigation |
|---|---|
| Extraction latency on retrieved chunks | Chunks are small (~200 chars each), extraction is fast |
| Event quality from focused context | Better than full-conversation extraction (less noise) |
| Token cost increase | Budget cap limits maximum; raw chunks dominate cost |
| Reader confusion from mixed format | Clear section labels in prompt |
